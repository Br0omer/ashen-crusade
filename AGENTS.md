# Правила работы ИИ-агентов с «Пепельным крестовым походом»

Этот файл действует для всего репозитория и дополняет `docs/roadmap.md`,
`docs/releases.md` и документы отдельных задач в `docs/`. При конфликте
требований сначала остановиться и запросить решение владельца проекта.

## Что представляет собой проект

- Игра — изометрическая ARPG на JavaScript, HTML5 Canvas 2D и CSS. Миграция
  на Godot, Unity или другой движок не согласована.
- Сайт публикуется через GitHub Pages из ветки `main`:
  `https://br0omer.github.io/ashen-crusade/`.
- Корневая страница, `/arch061/`, `/arch062/` и другие каталоги —
  самостоятельные сборки или экспериментальные просмотровщики. Их статус
  указан в `docs/releases.md` и `docs/roadmap.md`.
- Принятые сборки и контрольные копии **не изменять**. Для новой реализации
  или визуального эксперимента создавать отдельный каталог/версию, если
  владелец явно не согласовал иной путь.
- ART-02a (художественное качество ходьбы) не принят. Принятую кинематику
  не выдавать за принятую графику или интеграцию в игру.

## Порядок работы исполнителя

1. Прочитать задачу (Issue или согласованное описание), релевантные участки
   репозитория и `docs/roadmap.md`. Зафиксировать цель, ограничения,
   проверяемые критерии готовности и затрагиваемые файлы.
2. Проверить зависимости и предполагаемые побочные эффекты. Если изменение
   затрагивает принятую сборку, основную страницу или способ публикации,
   **остановиться до получения согласования**.
3. Работать в отдельной ветке от актуального `main`; коммитить только в неё.
   Не делать прямой push в `main`, merge, force-push или удаление веток без
   явного разрешения владельца.
4. Вносить минимальные изменения. Сохранять существующее управление с
   геймпада, поведение игры, точки крепления оружия и независимость
   контрольных сборок, если задача не требует их менять.
5. Выполнять относящиеся к задаче тесты. Базовые проверки репозитория:

   ```bash
   node tests/arch061-contract.cjs
   node tests/arch062-contract.cjs
   ```

   Отсутствие тестов для новой механики — повод предложить тесты, а не
   считать всю игру проверенной. Не утверждать, что проверки запускались,
   если они не запускались.
6. Обновить план/документацию, если изменились этап, критерии приёмки,
   ограничения или публикуемая сборка. Не отмечать задачу как принятую
   до явного подтверждения пользователя.
7. Открыть Pull Request с описанием сделанного, результатами проверок,
   рисками, ссылкой на тестовую сборку (если применимо) и остающимися
   вопросами. Сначала дождаться CI и независимой проверки.

## Требования к независимому ревьюеру (агенту-контролёру)

- Читать **фактический diff PR и связанные исходные файлы**, а не только
  описание или уверения агента-исполнителя.
- Сопоставлять результат с исходными критериями задачи, проверять
  неожиданные изменения, связанные зависимости и возможные регрессии.
- Проверять статусы CI и доказательства тестирования; по возможности
  самостоятельно воспроизводить важные проверки.
- Явно классифицировать вывод: `PASS`, `CHANGES_REQUESTED` или `BLOCKED`.
  Перечислять конкретные проблемы и путь к проверке их исправления.
- После исправлений смотреть **новый diff** и повторять проверку.
  Формальная отметка `PASS` не заменяет решение владельца проекта.

## Публикация и приёмка

- GitHub Pages публикует `main`; PR **сам по себе не создаёт отдельную
  тестовую ссылку**. Для визуальной проверки заранее нужен изолированный
  URL/каталог или отдельный preview-процесс.
- Проходящие тесты и успешный деплой показывают техническое состояние,
  но не закрывают задачи с визуальными/игровыми критериями.
- Проверка на Galaxy Tab S9+ с Xbox Series Controller и художественная
  приёмка выполняются владельцем там, где это указано в плане.
- Никакой агент не должен самостоятельно объявлять сборку принятой,
  изменять прошлые результаты приёмки или перезаписывать контрольные версии.

## Работа с моделями

- Разрешены облачные ИИ-сервисы для исполнения и независимого ревью.
- Локальные LLM, локальный инференс и скачивание весов моделей для этого
  проекта **не используются**. Рабочая машина — IDE, Git и инструменты
  запуска/проверки проекта, а не сервер инференса.
- Разделение на исполнителя и ревьюера — логические роли; конкретные
  облачные модели/провайдеры настраиваются отдельно и здесь не закреплены.
