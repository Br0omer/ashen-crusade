# Pipeline V2 — единая разработка Ashen Crusade в OpenCode

Статус: инфраструктурный кандидат. После merge нужна фактическая проверка на рабочей машине; успешный CI не доказывает работоспособность клиента OpenCode и не заменяет игровую приёмку.

## Цель

Одна сессия VS Code / OpenCode с **Architect**. Владелец сообщает идею или баг, отвечает на существенные вопросы и один раз утверждает план инкремента (включая создание PR). Архитектор сам управляет вспомогательными агентами и разрешёнными скриптами. Владелец отдельно просматривает итоговый PR и **лично делает merge**. Переключаться в другие чаты для Developer/Designer/Git Operator не требуется.

## Роли и модели

| Роль | Модель | Обязанности |
| --- | --- | --- |
| Architect (primary) | `openai/gpt-6.2-astra` | Единый чат, план, делегирование, контроль критериев, ограниченные Git-операции |
| Game Designer (subagent) | `openrouter/google/gemini-4-hydrogen` | Игровые правила, альтернативы, вопросы, дизайн-сводка; без записи файлов |
| Developer (subagent) | `openrouter/anthropic/claude-sonnet-5.5` | Код, ТЗ инкремента, тесты и **только локальный** коммит |
| Git Operator (subagent) | `openrouter/google/gemini-4-hydrogen` | Только `status` и `report`; чтение Git/CI/ревью |
| Reviewer + QA (GitHub Actions) | `OPENROUTER_REVIEW_MODEL` (сейчас Google Gemini 4 Carbon) | Проверка реального diff, требований, сценариев QA, регрессий, технических рисков |

Для GitHub Actions нужен существующий секрет `OPENROUTER_API_KEY`. Новые отдельные ключи для Game Designer и Git Operator не создаются: они используют уже настроенный OpenRouter в клиенте OpenCode. Если модель не доступна в установленном клиенте, остановиться с BLOCKED, не заменять модель без решения владельца.

## Маршрутизация

- **Механика / баланс / UI / анимация / враги / уровни:** Architect приглашает Game Designer и возвращает пользователю не более трёх существенных вопросов. Когда проект игрового поведения готов, пользователь утверждает его.
- **Тест / баг / инфраструктура:** Architect сам готовит технический план; Game Designer не вызывается без необходимости.
- В обоих случаях реализация запускается **только после явного утверждения плана**. Для одной задачи достаточно одного утверждения, если оно включает разрешение на локальную ветку, коммит, push рабочей ветки и создание PR.

## Последовательность

1. **Обсуждение:** Architect формулирует цель, область изменений, критерии приёмки, сценарии QA, исключения и риски.
2. **Согласование:** пользователь явно подтверждает план и разрешает подготовить PR. Это организационное подтверждение **в тексте чата**. Не притворяться, что оно равно системному `ask`: технические ограничения обеспечиваются командным allowlist и проверками скриптов.
3. **Ветка:** Architect вызывает только `node .opencode/scripts/git-flow.mjs status`, затем `node .opencode/scripts/git-flow.mjs start`. Последняя команда сама генерирует `feature/inc-YYYYMMDD-XXXXXXXX`, обновляет `main` через `git pull --ff-only` и создаёт рабочую ветку. Для уже согласованного ARCH-062 также доступна точная команда `node .opencode/scripts/git-flow.mjs start test/arch062-swap-fire`. Никаких shell-шаблонов `start *`.
4. **Реализация:** Architect передаёт утверждённую задачу и ветку Developer. Developer сохраняет `docs/increments/<тип>-<slug>.md`, где есть `## Цель`, `## Критерии приёмки`, `## Проверки`; затем изменяет только разрешённые файлы.
5. **Локальная проверка/коммит:** Developer может запустить только `node .opencode/scripts/dev-flow.mjs status`, `check` и `commit`. Скрипт не принимает аргументов и проверяет Git, файлы, ТЗ и тесты; делает **локальный** коммит.
6. **PR:** Architect после проверки отчёта Developer вызывает `node .opencode/scripts/git-flow.mjs publish`. Скрипт повторно проверяет защищённые пути, CI-контракты, родительский `main` и отправляет только ветку задачи; создаёт PR. **Не делает merge**.
7. **Ревью:** GitHub Actions запускает Contract tests, затем Gemini в режиме Reviewer + QA. Architect запрашивает `report`; проверяет, что ревью относится к текущему SHA, и докладывает `PASS / CHANGES_REQUESTED / BLOCKED / PENDING`.
8. **Приёмка:** владелец проводит ручную проверку игрового поведения/художественных изменений на нужном устройстве и вручную решает, объединять ли PR.

## Границы безопасности

- Вызовы shell для Architect и Developer разрешены **строго по полным строкам**; `shell: "*"` остаётся `deny` до точных исключений. Никаких аргументов, `&&`, `; `, `$()`, дополнительных git/gh/shell.
- Developer не может редактировать `.github/`, `.opencode/`, принятые сборки, кандидаты ART-02, ключи и основные файлы игры. Любое изменение защищённых путей блокируется Git-скриптом даже если инструмент редактирования допустил запись.
- Тестовые команды выполняют код локальной ветки и **не являются песочницей**. Для работы с недоверенными PR или секретами необходима отдельная защита. Использовать только собственные согласованные инкременты.
- Нет гарантированного аппаратного подтверждения `ask` в текущем GUI. Текстовое утверждение плана — мягкий процессный контроль; shell allowlist/проверки скрипта и ручной merge — технические границы. Если нужно формальное неотменяемое разрешение до каждого push, понадобится отдельный внешний механизм авторизации.
- Принятые `arch061/`, `arch062/`, рабочие root assets и художественные исследования ART-02 не изменяются этим PR. Принятие игрового поведения и визуальных ассетов — только владельцем.
- Автоматический merge, force-push, rebase, удаление веток, прямой push в `main`, локальный LLM-инференс запрещены.

## Первый сквозной тест

После merge и `Git: Pull` открыть **новую сессию** Architect в VS Code. Проверить доступ к Game Designer и его ответ на безвредный вопрос об уже согласованной механике. Затем передать Architect реальную задачу регрессионного теста ARCH-062: одновременные `RB + RT` в одном игровом тике. Согласовать план в чате. Architect должен создать ветку, передать работу Developer, получить коммит, создать PR и дождаться независимого ревью. **Не изменять** `arch062/`; тест разместить в `tests/`, критерии — `docs/increments/`.

Не считать Pipeline V2 завершённым до подтверждённого полного прохода на пользовательской машине.

## Бюджет

Целевой предел: **$100/мес.** Использовать дорогостоящую Astra только для Architect, Sonnet для кода, Gemini Hydrogen для Game Designer и чтения Git, Gemini Carbon один раз на подтверждённый CI. Избегать бессмысленных повторных ревью и полных пересказов многотысячных документов. Не обещать фиксированную стоимость: OpenRouter тарифицирует фактические токены, а дополнительная генерация изображений может потребовать отдельного бюджета.
